## Technical Implementation Details

### Multi-Tenant Testing Strategy

**DNS Resolution**:
- Local: `/etc/hosts` entries for tenant-a/b/c.test.local
- CI: Automated `/etc/hosts` configuration in GitHub Actions workflow
- Fallback: `X-Tenant-Subdomain` header override (if implemented)

**Tenant Fixtures**:
- Tenant A: Full-featured (loyalty enabled, consignment, 3 products, 2 gift cards, OAuth client)
- Tenant B: Standard (loyalty enabled, consignment, 3 products, 1 gift card, OAuth client)
- Tenant C: Minimal (loyalty disabled, 2 products, 1 gift card, no OAuth)

**Isolation Testing**:
- Product ID verification (no overlap between tenants)
- API-level cross-tenant access attempts (verify 404/403 responses)
- Storefront visibility verification (subdomain-based filtering)
- Feature flag enforcement (e.g., loyalty disabled in Tenant C)

### Test Data Seeding Pattern

**Seeding Script Architecture**:
1. Authenticate as admin for each tenant
2. Create tenant infrastructure (if not exists)
3. Seed users (admin, customer, consignor, loyalty member)
4. Seed products with variants
5. Seed gift cards
6. Configure loyalty program
7. Create OAuth clients

**Idempotency**:
- All POST requests wrapped in try/catch to handle 409 Conflict (already exists)
- Seeding script can be run multiple times without duplicating data
- Enables deterministic test data reset

### Performance Optimizations

**Parallel Execution**:
- Configured 4 workers in CI (`workers: 4` in `playwright.config.ts`)
- Tests run in parallel across files
- Each worker gets isolated browser context

**Selective Test Execution**:
- CI runs Chromium only for PRs (fastest feedback)
- Nightly runs full browser matrix (Chromium, Firefox, WebKit, Mobile)
- Developers can target specific browsers locally

**Video Recording Strategy**:
- Always record (not just on failure) for debugging
- Videos help identify timing issues in CI
- Retention: 14 days (balances storage cost vs debugging value)
