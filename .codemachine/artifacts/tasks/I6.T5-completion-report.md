## Deliverables

### 1. Backup Storage Infrastructure

**Files Created:**
- `modules/core-platform/src/main/java/villagecompute/storefront/backup/BackupStorageClient.java` - Interface for backup storage operations
- `modules/core-platform/src/main/java/villagecompute/storefront/backup/R2BackupStorageClient.java` - Cloudflare R2 implementation with checksum verification

**Features:**
- Upload/download with MD5 checksum verification
- List backups with prefix filtering
- Signed URL generation for external restore tools
- Automatic retry logic for transient failures

### 2. Database Backup Automation

**Files Created:**
- `modules/core-platform/src/main/java/villagecompute/storefront/jobs/DatabaseBackupJob.java` - Scheduled backup job

**Features:**
- **Daily Base Backups:** Full database snapshots at 3 AM UTC via `pg_basebackup`
- **Hourly WAL Verification:** Continuous monitoring of WAL archiving health
- **Automatic Retention Cleanup:** Old backups pruned after 30 days
- **Metrics Emission:** Prometheus metrics for monitoring (`backup.base.duration`, `backup.base.completed`, `backup.base.failed`)
- **Checksum Verification:** MD5 validation after upload to detect corruption

**Configuration:**
```properties
backup.storage.r2.endpoint=https://account.r2.cloudflarestorage.com
backup.storage.r2.bucket=village-storefront-backups
backup.retention.days=30
backup.postgres.host=postgres.storefront.svc
```

### 3. WAL Archiving

**Files Created:**
- `scripts/ops/wal-archive.sh` - PostgreSQL archive_command script

**Features:**
- Uploads WAL segments to R2 continuously (16 MB segments)
- Enables point-in-time recovery (PITR) with < 1 hour RPO
- Automatic retry on transient upload failures
- Structured logging for audit trail

**PostgreSQL Configuration:**
```ini
archive_mode = on
archive_command = '/usr/local/bin/wal-archive.sh %p %f'
```

### 4. Restore Automation

**Files Created:**
- `scripts/ops/restore-full-backup.sh` - Full database restore with optional PITR
- `scripts/ops/restore-pitr.sh` - Point-in-time recovery wrapper

**Features:**
- **Full Restore:** Downloads latest base backup + applies WAL files
- **PITR:** Restores to specific timestamp (e.g., "2026-01-10 14:30:00 UTC")
- **Environment Parameterization:** Dev/staging/prod via environment variables
- **Checksum Verification:** Validates backup integrity after download
- **Schema Validation:** Verifies database structure post-restore
- **Guided Next Steps:** Provides step-by-step instructions after restore preparation

**Usage:**
```bash
# Full restore
./restore-full-backup.sh

# Point-in-time recovery
./restore-pitr.sh --target-time "2026-01-10 14:30:00 UTC"
```

### 5. Tenant Lifecycle Management

**Files Created:**
- `modules/core-platform/src/main/resources/db/migrations/V20260122__platform_commands_audit.sql` - Audit table for platform operations
- `scripts/ops/tenant-suspend.sh` - Tenant suspension with feature flag backup
- `scripts/ops/tenant-resume.sh` - Tenant resume with feature flag restoration

**Features:**
- **Suspension:**
  - Updates tenant status to 'suspended'
  - Backs up feature flags to temporary table
  - Activates emergency kill switches (checkout, admin, storefront)
  - Logs platform command for audit trail
- **Resume:**
  - Restores tenant status to 'active'
  - Restores feature flags from backup
  - Removes kill switches
  - Logs platform command
- **HTTP 503 Response:** TenantResolutionFilter updated to return `503 Service Unavailable` with `Retry-After: 3600` header for suspended tenants

**Updated Files:**
- `modules/core-platform/src/main/java/villagecompute/storefront/tenant/TenantResolutionFilter.java` - Changed suspended tenant response from HTTP 403 to HTTP 503

**Usage:**
```bash
# Suspend tenant
./tenant-suspend.sh --tenant-id <uuid> --reason "Payment failure" --ticket "SUPPORT-123"

# Resume tenant
./tenant-resume.sh --tenant-id <uuid>
```

## Metrics & Observability

### Prometheus Metrics Emitted

**Backup Job Metrics:**
- `backup.base.duration` - Timer for backup job duration
- `backup.base.completed` - Counter for successful backups
- `backup.base.failed` - Counter for failed backups
- `backup.upload.duration` - Timer for R2 upload duration
- `backup.upload.completed` - Counter for successful uploads
- `backup.upload.failed` - Counter for failed uploads
- `backup.verify.completed` - Counter for successful verifications
- `backup.verify.checksum_mismatch` - Counter for checksum failures
- `backup.cleanup.deleted` - Counter for old backups deleted
- `backup.last.success.timestamp` - Gauge for last successful backup timestamp

**WAL Verification Metrics:**
- `backup.wal.file.count` - Gauge for WAL file count in R2
- `backup.wal.verify.completed` - Counter for successful verifications
- `backup.wal.verify.failed` - Counter for failed verifications
- `backup.wal.verify.no_files` - Counter for "no WAL files" warnings

### Alerting Rules (Documented in DR Playbook)

```promql
# Backup job failure
rate(backup_base_failed[5m]) > 0

# WAL archiving lag > 2 hours
time() - backup_last_wal_timestamp > 7200

# Backup age exceeds 25 hours
(time() - backup_last_success_timestamp) / 3600 > 25

# R2 storage errors
rate(backup_storage_upload_errors[5m]) > 0.05
```


   ```bash
   # Copy scripts to bastion host or backup pod
   scp scripts/ops/wal-archive.sh production-bastion:/usr/local/bin/
   scp scripts/ops/restore-*.sh production-bastion:/opt/restore/
   chmod +x /usr/local/bin/wal-archive.sh
   ```

   ```bash
   kubectl apply -k k8s/overlays/prod/
   # Deploys CronJobs, ConfigMaps, Secrets
   ```

   ```bash
   kubectl create job manual-backup-initial --from=cronjob/database-backup -n storefront

   kubectl logs job/manual-backup-initial -n storefront
   ```


## Known Limitations & Future Enhancements

### Current Limitations

1. **DNS Automation:** Tenant suspension script includes DNS status update as comment (requires DNS provider API integration)
2. **Backup Compression:** `pg_basebackup` uses built-in gzip (could optimize with zstd for better compression ratio)
3. **Parallel WAL Upload:** WAL archive script uploads sequentially (could parallelize for higher throughput)
4. **Managed Service Integration:** Restore scripts assume self-hosted PostgreSQL (managed services like RDS have different restore procedures)

### Future Enhancements

1. **Multi-Region Replication:** Cross-region R2 bucket replication for geo-redundancy
2. **Incremental Backups:** Use `pg_basebackup --incremental` for faster backups (PostgreSQL 17+)
3. **Backup Encryption:** Client-side encryption before R2 upload (additional security layer)
4. **Restore Time Optimization:** Parallel WAL apply during PITR (reduce RTO)
5. **Automated DR Drills:** Scheduled restore tests to non-production cluster (monthly)
6. **Tenant-Specific Restore:** Selective restore of single tenant data (for data recovery requests)
