# Task I1.T5: Migration Rollback Guide

## Overview

This guide documents the rollback procedure for the Row-Level Security (RLS) migration (`V20260113__enable_rls_policies.sql`) implemented in Task I1.T5.

**Migration File:** `modules/core-platform/src/main/resources/db/migrations/V20260113__enable_rls_policies.sql`

**Important:** Flyway (Quarkus default) does NOT automatically support down migrations. Rollback must be performed manually using the SQL script embedded in the migration file (lines 349-461).

---

## Prerequisites

- PostgreSQL access with superuser or schema owner privileges
- Backup of database before rollback (CRITICAL)
- Understanding of impact: Rollback removes ALL tenant isolation at database layer

---

## Rollback Procedure

### Step 1: Backup Database

```bash
# Production backup
pg_dump -U storefront -d storefront -Fc -f storefront_backup_$(date +%Y%m%d_%H%M%S).dump

# Development backup
pg_dump -U storefront -d storefront_dev -Fc -f storefront_dev_backup_$(date +%Y%m%d_%H%M%S).dump
```

### Step 2: Extract Rollback Script

The rollback SQL is embedded in `V20260113__enable_rls_policies.sql` from line 349 onwards (after `-- +migrate Down` comment).

**Option A: Extract automatically**
```bash
sed -n '/-- +migrate Down/,$p' \
  modules/core-platform/src/main/resources/db/migrations/V20260113__enable_rls_policies.sql \
  > /tmp/rollback_rls_policies.sql
```

**Option B: Copy manually**
Copy lines 349-461 from `V20260113__enable_rls_policies.sql` to a new file.

### Step 3: Execute Rollback

**Development environment:**
```bash
psql -U storefront -d storefront_dev -f /tmp/rollback_rls_policies.sql
```

**Production environment (USE EXTREME CAUTION):**
```bash
# 1. Put application in maintenance mode
# 2. Stop all application servers
# 3. Execute rollback
psql -U storefront -d storefront_prod -f /tmp/rollback_rls_policies.sql
# 4. Verify rollback success
# 5. Restart application servers
```

### Step 4: Verify Rollback Success

```sql
-- Connect to database
psql -U storefront -d storefront_dev

-- Check RLS is disabled on key tables
SELECT
    tablename,
    rowsecurity,
    forcerowsecurity
FROM pg_tables
WHERE schemaname = 'public'
  AND tablename IN ('tenants', 'users', 'products', 'orders')
ORDER BY tablename;

-- Expected result: rowsecurity = false for all tables

-- Verify helper functions are dropped
SELECT proname
FROM pg_proc
WHERE proname IN ('set_current_tenant_id', 'get_current_tenant_id');

-- Expected result: 0 rows (functions dropped)

-- Verify policies are dropped
SELECT
    tablename,
    COUNT(*) AS policy_count
FROM pg_policies
WHERE schemaname = 'public'
GROUP BY tablename
HAVING COUNT(*) > 0
ORDER BY tablename;

-- Expected result: No tenant isolation policies remain
```

### Step 5: Update Flyway History

Flyway tracks migrations in the `flyway_schema_history` table. After manual rollback, update the record:

```sql
-- Mark migration as rolled back (optional)
UPDATE flyway_schema_history
SET success = false,
    description = 'ROLLED BACK MANUALLY - ' || description
WHERE version = '20260113';

-- OR delete the migration record entirely (allows re-run)
DELETE FROM flyway_schema_history
WHERE version = '20260113';
```

**Warning:** Deleting the Flyway record allows the migration to re-run on next application start.

## Rollback Impact Assessment

### What Gets Removed

1. **RLS Policies** - All `*_isolation_policy` policies on tenant-scoped tables
2. **Helper Functions:**
   - `set_current_tenant_id(UUID)` - Sets session tenant context
   - `get_current_tenant_id()` - Retrieves current tenant ID
3. **Row Security Enforcement** - Tables no longer filter rows by tenant

### What Remains Unchanged

1. **Table schemas** - Tenants, users, products, etc. remain intact
2. **Data** - All existing tenant data is preserved
3. **Application code** - TenantContext, TenantResolutionFilter still exist

### Security Implications

⚠️ **CRITICAL:** After rollback, database-layer tenant isolation is REMOVED. The application MUST enforce tenant filtering in queries, or data leakage will occur.

**Before rollback:** PostgreSQL RLS prevents cross-tenant queries even if application code is buggy.

**After rollback:** Application code is the ONLY line of defense. A missing `WHERE tenant_id = ?` clause will leak data across tenants.

## Testing Rollback (Dry Run)

Use a transaction-wrapped dry run to test rollback without committing changes:

```sql
-- Start transaction
BEGIN;

-- Execute rollback script
\i /tmp/rollback_rls_policies.sql

-- Verify RLS disabled
SELECT tablename, rowsecurity FROM pg_tables
WHERE tablename IN ('tenants', 'users', 'products')
AND schemaname = 'public';

-- Verify functions dropped
SELECT COUNT(*) FROM pg_proc
WHERE proname IN ('set_current_tenant_id', 'get_current_tenant_id');

-- Rollback transaction (changes not committed)
ROLLBACK;

-- Verify RLS restored (should be 'true')
SELECT tablename, rowsecurity FROM pg_tables
WHERE tablename IN ('tenants', 'users', 'products')
AND schemaname = 'public';
```

## Re-applying RLS After Rollback

If rollback was performed for testing and you want to re-enable RLS:

### Option A: Flyway Re-run (if history record was deleted)
```bash
# Delete migration record from Flyway
psql -U storefront -d storefront_dev -c \
  "DELETE FROM flyway_schema_history WHERE version = '20260113';"

# Restart Quarkus dev mode (auto-runs migrations)
./mvnw quarkus:dev -pl modules/core-platform
```

### Option B: Manual Re-application
```bash
# Extract UP migration script (lines 1-347)
sed -n '1,/-- +migrate Down/p' \
  modules/core-platform/src/main/resources/db/migrations/V20260113__enable_rls_policies.sql \
  | head -n -1 > /tmp/reapply_rls_policies.sql

# Execute
psql -U storefront -d storefront_dev -f /tmp/reapply_rls_policies.sql

# Update Flyway history
INSERT INTO flyway_schema_history (version, description, type, script, checksum, installed_by, execution_time, success)
VALUES ('20260113', 'enable rls policies', 'SQL', 'V20260113__enable_rls_policies.sql', 0, 'storefront', 100, true);
```

## Rollback Checklist

Before executing rollback in production:

- [ ] **Backup database** (pg_dump with `-Fc` format)
- [ ] **Test rollback in staging** environment first
- [ ] **Put application in maintenance mode** (no active users)
- [ ] **Stop all application servers** (prevent query attempts during rollback)
- [ ] **Execute rollback SQL** from extracted script
- [ ] **Verify success** using verification queries above
- [ ] **Update Flyway history** table
- [ ] **Test application functionality** before re-enabling
- [ ] **Document reason for rollback** in runbook
- [ ] **Restart application servers** and monitor logs

## Conclusion

Rollback of V20260113 RLS migration is fully supported via embedded SQL script. The rollback:
- ✅ Cleanly removes all RLS policies
- ✅ Drops helper functions
- ✅ Preserves table schemas and data
- ⚠️ Removes database-layer tenant isolation (application must enforce)
- ⚠️ Requires manual Flyway history update

**Recommendation:** Only rollback RLS in emergency situations (performance issues, compatibility bugs). Tenant isolation is a critical security feature per ADR-001.
